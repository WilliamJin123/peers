# Peers: parallel sessions in one checkout

Date: 2026-10-25. Status: built, tested, installed 0.3.0 at user scope.

## Problem

William runs about five Claude Code sessions at once. Worktrees cost a merge per session and an install per worktree. One shared tree costs chatter: every session sees peer edits in `git status` and spends messages on "I will ignore that". Order of optimization: time first, then tokens.

## Target

A session behaves like a person on a shared document. It edits its own files. It sees a peer's cursor only on the file it is about to touch. It commits its own files. Tickets update themselves from what the session did.

## Shape

One Claude Code mod (`hooks/register.tsx`) and one CLI (`bin/peers.mjs`), one repo, installed with `/plugin install`.

| Part | Event | Cost |
|---|---|---|
| Ledger | `tool.call` on Edit, Write, NotebookEdit; Bash by dirty-file mtime snapshot before and after | host side, no tokens |
| Awareness | `tool.call` on Read and the edit tools: one `context` line when a peer touched that file since this session last read it | ~30 tokens, only on hit |
| Band | `ui.render` AbovePrompt from an atom refreshed every 3 s | none |
| Rule | `prompt.compose` adds one section | ~70 tokens per request, cached |
| Guard | Bash staging, discards, branch switches and writing formatters denied when they reach a peer's uncommitted file (`lib/guard.mjs`); Write denied when it drops a peer's uncommitted lines | none |
| Scoped git | `peers status|diff|commit|check` | one command each |
| Tasks | `peers ready|claim|close` on Backlog.md; commit appends the sha to the task notes | one command each |

Ledger: `~/.claude/peers/<encodeURIComponent(root)>/<session>.json`. One writer per file, so no locks.

Agent-neutral core (0.8.0). `lib/core.mjs` holds the ledger, the Bash snapshot, the guard and the Write deny over a small io (read, write, list, stat, run, now). The mod binds it to `$` per call; `lib/io.mjs` binds it to node. `lib/agents/{codex,cursor}.mjs` map each agent's hook JSON to one event shape and back. `lib/hook.mjs` runs one event per process; the snapshot waits in `~/.claude/peers-run/snap/` for the post event.

## Decisions

- Hunk-level attribution (2026-10-26, William: the four gaps are core, not convenience). Each edit records the distinctive lines it added and removed. `peers commit` keeps a peer's hunks out of the commit.
- A private index from HEAD plus `commit-tree` and a compare-and-swap `update-ref`. The 10-06 lesson (`-U0` patches with dropped hunks shifted lines) is why the blob is built in code from the base text, never with `git apply --unidiff-zero`.
- Claude Code's Write already refuses a file changed since the last Read. The mod's Write deny covers the rest: a fresh Read, then a whole-file Write that loses a peer's lines.
- `peers check` uses `~/worktrees/<repo>-check`, never the push worktree.
- Board: Backlog.md (2026-10-25, replaced beads): plain Markdown, git history, GitHub audit without a shell. The agent never edits status itself. `peers` does.
- No MCP, no server. Hooks and a CLI only.
- Board adapter (2026-10-27, 0.16.0): one interface (`ready`, `claim`, `note`, `open`, `close`), one adapter per tracker, picked by `board` in the config. Against shell templates in the config (fragile quoting on Windows). Jira by acli (default, uses the user's own login, no token in peers) or REST.
- Action log and outbox (2026-10-27, 0.16.4). Options: A keep direct board calls (lost notes, no trace); B an append-only action log per session with board writes as pending sends, retried on the next command; C event-source the whole ledger (every edit an event; rewrites the core, and the edit hook fires on every write). Ranked: no lost board writes, a readable trace, no change to hunk ownership. Chose B. Claim stays direct (it must fail loud); close's status move must land or the ticket stays bound.
- Ledger cost (2026-10-27, 0.16.6). Measured: the largest ledger 808 KB, 70% of it whole-line keys in `edits` of committed files; read 6 ms, write 6 ms per edit. Each session read every peer ledger and ran `git status` every 3 s (about 50 ms). Options: A cache by mtime (ledger parse; `git status` keyed on index, HEAD and ledger times, 30 s cap) and drop committed keys; B the view server as the only reader (one status per repo, but the band then depends on the server); C an append-only ledger (cheap writes, but every reader folds a log and needs compaction). Ranked: fewer process starts (each flashes or costs more on Windows), no new failure modes, no format change. Chose A. B waits for numbers from Windows. C is not worth it after A: the largest ledger drops to 367 KB, a write to about 3 ms.
- Server lifecycle (2026-10-27, 0.16.7). A plugin update left the detached server on the old code; only launchd's `--install` restarted it, and the stop used `ps` and `lsof` (none on Windows). Options: A each client pings the version and stops an older server over HTTP; B a pid file and `process.kill` (pid reuse, stale files); C the server watches its own plugin dir and exits on a change (per-OS fs watch quirks, no help for the client that must start the new one). Ranked: works the same on every OS, no new state on disk, no OS tools. Chose A. `/api/stop` takes only local POSTs with `x-peers: stop`. Servers before 0.16.7 answer ping as text and have no stop: one manual kill.
- Platform layer (2026-10-27, 0.17.0). OS code sat in 8 places as inline `process.platform` checks; a missing OS (`lsof` on Windows, `--install` off macOS) showed only at run time. Options: A one object per OS in `lib/platform.mjs` with the same keys, methods that return argv or file text and run nothing, a `.d.mts` contract, and a test that holds every OS to every key and finds any OS branch outside the file; B keep inline checks plus a lint rule (misses tools that exist on one OS only); C npm packages (`open`, `ps-list`, `cross-spawn`: none covers shims, hooks or a supervisor, and peers has no dependencies). Ranked: a gap fails CI before release, works for both node and the mod, no dependencies. Chose A. The types check nothing at run time; the test does. Windows gets a supervisor: a Startup-folder VBScript loop (hidden, restarts on exit); CI installs it on the Windows runner. Linux gets a systemd user unit. `peers doctor` reads the result.
- Bash attribution by name (2026-10-28, 0.17.1, WA-932, WA-933). Two Bash commands ran at once; the time window gave a file to the wrong one. Options: A the command whose text names the file wins, then span; B watch writes per process (fs_usage, dtrace, ETW: root on macOS, a new path per OS); C serialize Bash commands per repo (blocks real parallel work). Ranked: correct for the common case, no root, no new OS code. A taken, plus `peers take` to fix the rare miss by hand. Same fix: `rootOf` on a folder not made yet walks up and caches no miss; that miss lost every Write in a new folder.
- Band colors from the server (2026-10-28, 0.17.1). The band read the pane's index (stale while the pane was shut) or a local rule over another session set, every 3 s. Options: A the server sends its color order; the mod listens to a sig-only event stream and reads the order on each change; B the band polls the full index every 1 s (about 100 KB per read per session); C each session writes its color into its own ledger (a new field every client must agree on, still read by poll). Ranked: band equals pane, low cost, no new state. A taken.
- One id per process (2026-10-28, 0.17.2, WA-936). A /resume changed the id in `~/.claude/sessions/<pid>.json` and in Bash's env; the mod kept `$.session.id()` from start. Options: A the running list is the id: the mod finds its pid and follows that file, merging the old id's ledgers; B every reader unions an alias list kept in the ledger (each reader changes, aliases grow); C read `$.session.id()` per event (whether the engine updates it on /resume is not documented). Ranked: one id everywhere, the source liveness already uses, no reader change. A taken.
- One open-file rule (2026-10-29, 0.18.1, WA-945). 0.17.3 put `holding` (lines still differ from HEAD) in the guard and the CLI only. The band, `peers ls` and the view's author list still used "no own commit since", so a peer stayed on files that someone else had committed. WA-945 was the same rule split across a version skew: the session's mod was loaded before 0.17.3, and its guard blocked a file that the new CLI called whole and mine. Now every reader uses `holding`. The band's cost is one `git show` per file only after the file, the index or HEAD moves (`liveNow`, cached by mtimes). A mod loaded before an update still runs old code until the session restarts.
- Names from the running list (2026-10-29, 0.18.2). The band showed `dir/cc-xxxx` in place of `/rename` names. The transcripts run 40 to 220 MB. One perl scan past 5 s turned perl off for the session's life, and the fallback `$.fs.read` rejects files over 4 MiB, so every name came back empty. `~/.claude/sessions/<pid>.json` holds `name` and `nameSource: "user"`, the source that liveness already reads. The name now comes from there. The transcript gives only the AI title. A failed scan keeps the last titles found, and only a missing perl turns perl off.
- Loaded mod version (2026-10-29, 0.18.3). An open session keeps the mod it loaded, and the CLI runs the install. WA-945 and the stale band names came from that skew, and nothing showed it. Each mod now writes `~/.claude/peers-mods/<pid>.json` (version, session, time) at `session.start`, which a reload runs again. `peers doctor` joins those files with the running list and names each session that runs an older mod. Keyed by pid: the set stays as big as the pids that ran, and a file older than its process marks a reused pid. Rejected: a version field in each ledger (a session with no edits has none, and one session has a ledger per repo).
- Close names live commits (2026-10-29, 0.18.4, WA-970, WA-975). `peers close` used the sha it kept at commit, which a squash or a rebase makes stale. It now runs `git log --grep '^Ticket: <id>$' HEAD` in each repo this session has a ledger in. The trailer survives a squash. With no trailer, it falls back to the kept sha only while HEAD still contains it. Same release: a ledger entry with no line data held a file for as long as it was dirty. A 10-24 entry merged on /resume blocked edits days later. It now stops holding once a commit after its last edit touches the file. Trade-off: if such a peer still has uncommitted lines and someone else commits the file, the guard no longer protects those lines.
- Paths and reach (2026-11-02, 0.18.5). birdwatch dev reported that `peers commit -- <dir>` left out memo.md: one Bash command wrote it with a heredoc, then ran the commit, and the ledger records a command's writes only after the command ends. A named path now also takes its dirty files that no live session holds. Files a peer holds stay out, and the commit names them on stderr. Same day: my session took 4 of birdwatch's run files in tasks. My command named nothing there, but the guard watches every repo a session touched, and birdwatch's long command had not recorded them yet. A command now takes writes only in the repos it reaches: its cwd, a `cd` target, a named absolute path. The guard and the warning still watch every touched repo. Trade-off: a script that writes into another repo without naming it leaves those files unclaimed; `commit -- path` or `take` claims them. Rejected: a ref-lock retry on push. peers runs no push; it belongs to each repo's push script.
- HEAD side cached (2026-11-02, 0.18.6). During an 80-minute birdwatch run, load went to 500–900 and forks failed. A subagent appended to many untracked JSONL files, and 6 sessions held some of them. Each held file cost 2 git forks (`git show`, `git log -1`) per command and per 2 s band tick, in every session, because the cache key had the file's mtime. 0.18.4 added the `git log` call, and for an untracked path it walks all history. Now `HEAD:rel` and its last commit time are cached on repo state only: index, HEAD and the reflog cover commit, amend, `reset --soft` and checkout. A path not in HEAD gets no log call. An append costs a file read and no fork. Rejected: a per-path rate limit, or a skip for append-only files. Both hide the cost and keep it. Open: a short command still takes a peer's writes while the peer's long command runs, because the peer records them only at its end. Fix candidate: an in-flight record `{from, reach}` that other sessions yield to. Not decided.
- Running commands yield (2026-11-02, 0.18.7, William agreed). Each shell command writes `{from, reach}` to `~/.claude/peers-run/acts/<session>.json` when it starts and removes it when it ends. A command takes no unnamed write in a repo where a peer's command, begun before it, still runs. The peer takes those writes when it ends. A named file (in the command text, or a tool's file) stays with the command that named it. A record older than 15 min counts as stale: Bash runs at most 10 min in the foreground. Trade-off: your own unnamed shell write during a peer's long run goes to that peer; `peers take` moves it back. A background command records at launch, so it is not covered. Rejected: one record in the ledger, because a ledger write on every command makes every peer parse it again.
- View server off the event loop (2026-11-02, 0.18.8). `/api/ping` took 4–8 s, and some requests timed out. Each rebuild ran 5 sync git calls in each of 16 repos, about 450 ms at low load, much longer at high load. Any watcher event rebuilt every repo, and a request after a change waited for the rebuild. Now git runs async. A repo's files are built again only after its tree, index, HEAD or one of its ledgers moved. One build runs at a time, in the background. A request gets the last build, and only the first request waits. Measured during back-to-back rebuilds: worst ping 680 ms before, 72 ms after. Trade-off: a read right after a change can show the build before it. The SSE push sends the new one when it is done. Rejected: a worker thread. state() reads caches that the main thread fills (titles, labels, subjects).
- Readers take no writes; the trailer follows the subject (2026-11-02, 0.18.9). autobrowse work saw `git fetch && git log && git status` blamed for WA-998's files. A command where each program is a reader (git log/show/status/diff/fetch, gh except download/checkout, rg, cat, sed without -i, find without -delete/-exec) and output goes only to a stream or /dev/null records nothing and makes no peer yield. A reader list, not a writer list: an unknown program counts as a writer, so a miss costs a wrong blame, never a lost write. `peers close` named WA-1010's commit for WA-1012: the commit had the bound ticket's trailer while its subject said `(WA-1010)`. Now ids of the bound ticket's prefix in the subject's parentheses set the trailer and the board note when the bound id is not among them. Rejected: refuse the commit (blocks work for a label). Ids in prose ("after WA-932") do not count.
- GitHub Issues board (2026-11-04, 0.19.0, William asked). Through `gh`, as Jira through `acli`: the login is gh's, peers holds no token. Ids are full, `owner/repo#12`: a bare `#12` in a trailer links only inside its own repo, and `close` from another cwd would hit the wrong repo. The views cut it to `#12`. In Progress is a label: Issues have only open and closed, and a Projects v2 status field needs GraphQL and a project per repo. Open `- [ ]` boxes in the body hold `close`, as Backlog.md's criteria. Rejected: `Fixes #12` in the trailer (GitHub closes on push, past those checks); subject ids for GitHub (a squash merge adds `(#45)`, a PR number). Checked live by `scripts/smoke-github.sh`: 14 checks on a throwaway private repo, the commit on the issue timeline among them.
- Concurrent commands and shared lines (2026-11-04, 0.19.1). WA-1077's 10-minute test run took the lines of WA-1076's biome rewrite, made while it ran. The rule "a command still running takes the unnamed writes" covered only a command that began before ours. A later one still running was invisible, so the earlier one took its write when it ended. WA-1076's own record then dropped those lines as a peer's. Now a write made after a still-running peer command began is left to it: the last command to end takes it. Trade-off: a long command's own write made during a short one goes to the short one. A long run is mostly tests, a short one an edit or a formatter, so the short one is the better guess. Also, the guard, the Edit warning and `peers commit -- <file>` now count lines as `peers diff --who` does: a line both sessions claim counts for neither. Before, `diff --who` said "yours" while the guard blocked biome and the commit. Rejected: a push warning for peers' commits. Nearly every push in a shared checkout carries them, and CI is the gate (push.sh).
- Race audit (2026-11-04, 0.19.2 and 0.19.3, William asked after 0.19.1). Fixed, each with a check that fails on the version before the fix: (1) Two parallel tool calls in one session read, changed and wrote the ledger at once, so one lost its lines. Now one write per file at a time per session. The queue lives in the session's state: 0.19.2 kept it per dispatch, so the mod still raced. (2) A read during a write saw half a file. `peers` then started a fresh ledger over the real one, and a peer dropped out of the guard. Now node writes go to a temp file, then rename. The mod's `$.fs.write` has no rename, so readers retry, keep a peer's last good parse, and never write over a file that does not parse. (3) `peers commit` held the ledger for the whole commit and wrote it back, dropping edits the mod recorded meanwhile. Its save now merges newer entries and commits from disk. (4) A commit's time came after the commit, so an edit made during it looked committed. Now it is the time before the files are read. (5) A begin and a finish of the session's acts at once each wrote the file from one old read. The finished act came back for 15 minutes, and peers left it every unnamed write. Or a running act was dropped, and peers took its writes. Now acts writes go through the same queue. `record` never throws: a hook that throws after its tool ran could run the tool again. Left open: a background command's act ends when its call returns, while it still writes, because the mod API has no event for its end. Codex hooks run in a new process per event, so (1) and (5) can still happen there. A mod write can still land between the CLI's merge and its rename (milliseconds). Rejected for now: an append-only event log or a broker. These were rule and write bugs, not transport. Revisit if attribution breaks again.
- Place beats start time (2026-11-05, 0.19.4, WA-1067.10's session reported it). This reverses the 0.18.7 tie rule that William agreed to. A peer's 2-min Playwright run in `packages/ui` took the drizzle output, the biome rewrite and the ffmpeg frames that a short command wrote while it ran. 0.18.7 left every unnamed write to a still-running command that began first. Now each act also records its places: its cwd, each `cd` target, and each path word (a named dir counts). An unnamed write goes to the command that names it, else to the command with the deepest place that holds it. On a tie, the command that began inside the other's span takes it (0.19.1 kept). A long reader in another dir takes nothing. Trade-off: two commands at root with no path words tie, and the shorter span takes the write, as 0.19.1 did for a later command. Also: (1) a hunk that no session recorded is "no one's". `peers commit` leaves it and says so (`peers take` or `--whole`). Before, it counted as mine: a commit took 22 lines of a peer's stories. (2) An own entry with no lines, older than a commit of the file, is out of my files. A stale entry from 10-28 had put a peer's file in scope. (3) The CLI retries a peer ledger that does not parse (6 times, 20 ms). Before, it dropped that peer silently. Not proven: why the peer's ledger lacked those keys at 17:18. A torn read of its 2.6 MB ledger is the likely cause; (3) covers it. 0.19.5 (WA-1096 again, same day): a session reloads the mod only when its turn ends, so a peer in a long turn kept writing 0.19.3 acts (no places, no cmd). 0.19.4 read such an act as working nowhere and took its writes: a read-only `node -e` of this session took a line of a peer's `sed` on store.ts. Now an act without places keeps the 0.19.3 rule (leave it all). Also `peers drop <file>`, take's reverse, for a write a command took by mistake. The report that started 0.19.5 (drizzle files credited to a peer's typecheck) was 0.19.3 on both sides: the peer ran it before the reload.
- Ledger size cap (2026-11-05, 0.19.6, WA-1100; WA-1099's session reported it). The mod's `$.fs.read` rejects a file over 4 MiB. core read every read error as "no ledger", so the mod wrote a fresh, empty ledger over a 4 MiB one: a session lost 18 files it had just taken, and the guard blocked it on them again. 97% of a big ledger was keys of clean files (committed or reverted), kept forever. Now: (1) a file that is there but unreadable is TORN: no write, the record skips. (2) A ledger past 1 MiB drops the entries of clean files on its next write, in the mod and in the CLI. Their old keys only mislead a later edit of the same file. (3) Still past 3 MiB: the biggest entries lose their keys and hold the whole file until a commit, as an old mod's entry does. Rejected: hashed keys (old mods compare text, and sessions run mixed versions until their turn ends); a ledger per file (a format change every reader must learn).
- Claims: one truth, seen on every board (2026-11-07, 0.20.0, WA-1178, William: "one truth is fine, but I want to see who holds what"). The board said In Progress for 16 of 18 tasks with no live holder; a session kept old tickets in its other repos' ledgers. Options: A ledger only, the views join it at read time (one truth; the board, GitHub and Jira show nothing); B the board's assignee as the truth (two truths, stale names, sessions are not GitHub or Jira users, and `@william` already means "his call"); C the ledger as the truth, peers projects it into the board in the same write as the status, a sweep repairs drift, like a controller (a cache peers owns, no extra commits); D an append-only claims log in the tasks repo (principled, more machinery, a commit per heartbeat or none at all). Ranked: one truth, visible where people look, no churn, never undo a person's move. Chose C. The status was already a projection; the holder rides in the same edit. Backlog.md: `@peers:<name>` assignees beside the board's own, which peers never touches. GitHub and Jira: assignees are real accounts, so the claim names the session in a comment, and their sweep reads holders as unknown. Sweep (`peers sweep`, also in `peers ready`): marks follow the live claims; a task that only dead or replaced claims name goes back to To Do; one no claim ever named is reported, never moved. A claim holds while its session is in the running list, however idle, plus 2 h after its last write (a /resume). One task per session: the latest claim; `claim` clears the ticket in the session's other ledgers, and readers ignore leftovers from before 0.20.0. `peers held` lists holders from the ledgers alone. No new mod: the band and pane already show each session's ticket, and the board's own UI now shows the holder. Trade-offs: the sweep writes only from a CLI run, so drift lasts until the next `ready`; claim clears another of my ledgers with a read-modify-write that can race a mod write by milliseconds.
- Claims review (2026-11-08, 0.20.1, William: "double check, polish, finalize"). `scripts/smoke-claims.sh` runs the real CLI on a throwaway HOME, board and two repos (12 checks); it found that the first claim on a fresh install crashed (no `~/.claude/peers` yet). Also fixed: a claim made in one repo now binds `commit` and `close` in the session's other repos (one task per session, read only for those two commands); `close` waits only for live current claims, so a leftover ticket no longer blocks it; its message named the ticket, not the session; GitHub's sweep no longer reports claims on another repo's issues; notes are grouped in two lines. Real data showed tickets in ledgers from before 11-07 (no `claimed`) on Done tasks, coming back as a session's claim after it closed its real one. Now such a ticket counts for nothing (not held, not dead, no release), and `close` clears every ticket in the session's ledgers. Trade-off: a session that claimed before 11-07 and still works shows as no holder until it claims again; the sweep only reports its task. Lesson: `BACKLOG_CWD` sends every `backlog` call to the real board, whatever the cwd. A first test landed 4 commits there (reverted); the smoke sets it to the throwaway board.
- Claims race review (2026-11-08, 0.21.0, William: "check race conditions and edge cases; it looks like hunk attribution, which had many bugs"). Found, each shown by a run: (1) a sweep in one session during another's claim sent the claimed task back to To Do, and no later sweep moved it back (claim wrote the board, then the ledger, with seconds of push hook between; `race1.sh` showed `To Do` with the claim live); (2) the mod's ledger write (read, change, write) could drop a claim the CLI wrote between, the hunk-attribution bug class; `unbind` wrote a stale copy of another ledger and could drop file entries the same way; (3) a dead claim stayed forever, so a task a person set In Progress again later went back to To Do on every sweep; (4) a crash leaves its running-list file, so its claim held forever; (5) two claims at once kept one mark; (6) a board error read as "no task"; (7) a closed session's mark changed name (the running list has no name for it), one board commit per flip. Options for where a claim lives: A keep it in the per-repo ledgers and guard each write (the mod copies claim fields from disk before it writes; still a millisecond window, and the mod has no lock); B one claim file per session, written only by the CLI under a lock (one writer, so no lost update; one file, so one task per session by construction; readers join it to ledgers); C an append-only claims log (D in the 0.20.0 entry: more machinery for the same result). Ranked: no lost update by construction, then fewest moving parts, then no reader churn. Chose B. `~/.claude/peers-claims/<session>.json` (outside `~/.claude/peers`, which tools list as repos), with the board lock as `.lock` (mkdir; a dead pid or 2 min frees it). Claim: lock, claim file, board, title; a board refusal puts the old claim back. Close: lock, board, delete. Sweep: lock (skip if busy 15 s), plan, write, then delete the dead claims it answered for, so a dead claim frees its task once. Liveness: the running list with dead pids dropped, else the session's latest ledger write or the claim, plus 2 h. The claim keeps the holder name it was made with. `/resume`: the mod moves the claim to the new id. 0.20 ledger claims move to files once (`.from-ledgers` marks it); ledger tickets are ignored after. Removed: `current`, `unbind`, the cross-repo `away` lookup and the leftover rule. `scripts/smoke-claims.sh` has 24 checks, the races among them (a slow fake board). Left: claims are per machine (a board two machines share sees the other's tasks as unheld); a pid reused after a crash keeps that claim until the new process ends; a session resumed after its 2 h grace finds its task freed and claims again.
- Many machines, one board (2026-11-08, 0.22.0, William: "I might use this for multi tasking, multi machine, multi engineer workflows"; "others need to know the person who claimed it, or the particular agent; the owner of many sessions needs that extra detail"; "A is fine, as long as it supports eventual consistency"). Before: a machine's sweep read every holder mark as its own, so it dropped other machines' marks and sent their tasks back to To Do. Options: A each machine writes only its own holders on the board (`<who>/<session>`), reads the rest; no new store. B claims in a shared git repo (the tasks repo): one truth, but push and pull on every claim, merge conflicts, and a git dependency for GitHub and Jira users. C board leases with heartbeats: a comment or field each N minutes; churn on the board, and a sleeping laptop loses its task. D a hosted lease store (Redis, a DB): strong, but a service to run, against the self-hosted rule. Ranked: no wrong write to another machine's task, then no new storage, then no board churn. Chose A. Holder = `<who>/<session name>`; who = config `who`, else user@host. Backlog.md: `@peers:<holder>` assignees; an edit keeps others' marks (`-a` sets all, so it re-reads first). GitHub and Jira: an append-only comment log, replayed (`holds this`, `lets go`; the queue comment and `Done:` clear). Eventual consistency: each holder has one writer (its machine); each write is idempotent and computed from the board's state, never from a cached one; each sweep re-asserts its own marks, so a lost Backlog update (two machines' `-a` at once) heals on the next sweep. Release re-reads the board: it queues only when no other holder is left, and says so; else the dead claim stays, so the last machine out queues it, also when two let go at once. `close` waits on other machines' holders and on GitHub and Jira assignees other than you.
